## 1. Requirements Normalization

**Original prompt (verbatim intent):** Build a URL shortener with core APIs, analytics,
and reliability features, orchestrated through an agentic SDLC pipeline.

**Normalized engineering problem statement:**

Build a service that accepts a long URL and returns a shortened, unique alias that
redirects to the original on request, with basic usage analytics per link (click count,
timestamp, referrer) and reliability characteristics appropriate to a public-facing
redirect service (availability under load, graceful handling of invalid/expired/malicious
input, no data loss on writes). Custom aliases, link expiration, and auth/ownership are
out of scope for v1 unless a scenario calls for them.

**Ambiguities identified + assumptions made:**

| # | Ambiguity in the prompt | Assumption chosen | Rationale |
|---|---|---|---|
| 1 | "Unique" — unique for how long / at what scope? | Alias is unique for the lifetime of the system (no reuse, even after a link is deleted) | Simpler to reason about; avoids dangling-reference bugs if an old alias gets reassigned |
| 2 | "Shorter" — how short, fixed or configurable length? | Fixed-length alias (7 chars, base62) generated by the system; no user-chosen length | Keeps collision/generation logic simple for MVP; custom aliases become the greenfield scenario instead of baseline scope |
| 3 | Collision handling — what happens if a generated alias already exists? | Regenerate and retry on collision, bounded to N attempts before failing the request | Matches the "bounded retries" pattern already required in the orchestration layer — reuses the same pattern in domain code |
| 4 | "Analytics" — what's actually tracked? | Click count, timestamp, and referrer per link; no user auth or per-user dashboards | Assignment says "analytics" without specifics; this is the minimum that's meaningfully analytics rather than just a log |
| 5 | "Reliability features" — what does this mean concretely? | Idempotent creation (same long URL within a window optionally returns same short URL), input validation (malformed/malicious URLs rejected), graceful 404 on unknown/expired aliases | Concrete, testable behaviors rather than a vague "make it reliable" |
| 6 | Expiration / TTL — do links expire? | No expiration for v1; noted as a limitation | Keeps MVP scoped; reintroduced deliberately in the brownfield scenario rather than baked in upfront |

## 2. Stage Graph (locked)

**Nodes:** requirements → design → {implementation, test-planning, docs-drafting} → test-execution → docs-finalize → release-readiness

**Structure:**

```
requirements
   ↓
design  ── (exit gate: design approved)
   ├──→ implementation ──┐
   ├──→ test-planning ───┤
   └──→ docs-drafting ───┤
                          ↓ (sync point A — implementation must exist)
                       test-execution
                          ↓
                       docs-finalize  (folds in real behavior once tests exist)
                          ↓ (sync point B)
                    release-readiness
```

**Edges / parallelism:**
- design → {implementation, test-planning, docs-drafting} — parallel fan-out, all three gated only on design approval (none need each other's output to start)
- {implementation} → test-execution — test-execution needs real code to run against, so it waits specifically on implementation (sync point A)
- test-planning's output feeds test-execution's inputs but doesn't block its start
- {test-execution, docs-drafting} → docs-finalize — docs get finalized once real test behavior is known, folding in outcomes (sync point B, loosely — docs-finalize can begin once test-execution completes)
- {test-execution, docs-finalize} → release-readiness — final sync point before human sign-off

**Rationale for this shape:** implementation, test-planning, and docs-drafting can genuinely proceed independently once design is approved — none of them need each other's *output*, only the approved design. This is the real parallelism, not simulated. Test-execution is the one hard dependency on implementation's actual output (code to run), which is what makes it a true synchronization point rather than an arbitrary one.

    { "stage": "", "decision": "", "rationale": "", "timestamp": "", "actor": "agent | human" }

## 4. Gates (locked)

Each condition below references a concrete field from the Section 3 schema — checkable
predicates, not descriptions, so each gate can be pointed to directly in review.

| Stage | Entry condition | Exit condition |
|---|---|---|
| requirements | `overall_status == pending` (run initiated) | `requirement.normalized` non-empty AND `requirement.assumptions` populated |
| design | `stages.requirements.status == complete` | `stages.design.status == complete` AND a `decisions` entry exists with `stage == "design"` and `actor == "human"` (design approved) |
| implementation | `stages.design.status == complete` | code artifact(s) present in `artifacts.implementation` AND compiles/lints clean |
| test_planning | `stages.design.status == complete` | test plan artifact present in `artifacts.test_planning` |
| docs_drafting | `stages.design.status == complete` | draft doc artifact present in `artifacts.docs_drafting` |
| test_execution | `stages.implementation.status == complete` (sync point A) | `stages.test_execution.status == complete` AND all tests pass (no unresolved failures in `history` for this stage) |
| docs_finalize | `stages.test_execution.status == complete` AND `stages.docs_drafting.status == complete` | finalized doc artifact present in `artifacts.docs_finalize`, incorporating real test outcomes |
| release_readiness | `stages.test_execution.status == complete` AND `stages.docs_finalize.status == complete` (sync point B) | `approvals.release_readiness.decision == "approved"` (human sign-off recorded) |

**Note:** implementation, test_planning, and docs_drafting share the same entry condition
(design complete) but have independent exit conditions — this is what allows them to run
in parallel rather than gating on each other.

## 5. Human Approval Checkpoints

Implemented via `StageDef(requires_approval=True)` in `orchestrator/graph.py` +
the blocking CLI prompt in `orchestrator/approval.py`. Two checkpoints, deliberately
not more:

1. **`design` exit** — before any code/tests/docs get written. This is the point
   where the cost of a wrong call is cheapest to catch (nothing downstream exists
   yet) and most expensive to miss (implementation, test_planning, and
   docs_drafting all fan out from it in parallel — an unreviewed design mistake
   would propagate into three branches simultaneously, not just one).
2. **`release_readiness` exit** — the final sign-off before the pipeline
   would consider the run "done." Everything upstream (implementation, tests,
   docs) is real by this point, so this is a genuine "ship it or not" decision,
   not a formality.

**Why not more checkpoints:** implementation/test_planning/docs_drafting/
test_execution/docs_finalize are intentionally *not* approval-gated — they're
mechanically checked by their exit gates (compiles clean, artifact present, tests
actually pass) instead. Gating every stage on a human would turn "controlled
autonomy" into "no autonomy"; the two checkpoints above are the two points where
the decision is genuinely judgment-based (is this the right design? is this
actually ready to ship?) rather than something a predicate can verify.

**Rejection behavior:** rejecting either checkpoint (`reject <reason>`) raises
`ApprovalRejected`, which the runner treats as an immediate rollback + safe-stop
(`overall_status = "blocked"`) — no retry, since re-running identical content
against a human "no" isn't a transient failure. See Section 6.

## 6. Retry / Fallback / Rollback Rules

Implemented in `orchestrator/retry.py` + `orchestrator/runner.py`, verified by
`tests/test_orchestrator.py` (retry-within-budget, retry-exhausted, fallback-used,
rollback-scoped-to-one-stage, genuine-parallelism).

**Retry:** on handler exception (`StageFailure`) or a failed exit gate (`GateFailure`),
the runner re-attempts the *same* handler up to `max_retries` extra times (default 2,
i.e. 3 attempts total) — no state is undone between retries, since a retry means "try
again," not "change approach."

**Fallback:** once retries are exhausted, the runner makes exactly one attempt at a
registered fallback handler (a simpler/degraded implementation of the stage). Success
marks the stage complete with a `fallback_used` audit event, so the run keeps going but
the audit trail shows a degraded path was taken. No fallback registered (or the
fallback itself throws) falls through to rollback.

**Rollback:** restores only the failing stage's own slice of state — its `StageState`
(status/timestamps), its `artifacts` list, and its `retry_counts` entry — to the
snapshot captured immediately before its first attempt. It deliberately does **not**
touch `history`/the audit log (the failure trail must survive) or sibling stages'
state (so a failure on one parallel branch, e.g. `implementation`, can't clobber
progress already made on `test_planning`/`docs_drafting`). After rollback the stage is
marked `blocked` and the whole run's `overall_status` becomes `blocked` — a safe-stop:
the run does not continue past a blocked stage, and resuming requires human
intervention (fix the underlying issue and start a new run, or — future work —
resume-from-run-id).

| Stage | Max retries (default) | Fallback behavior | Rollback trigger |
|---|---|---|---|
| any stage (generic default via `DEFAULT_POLICY`) | 2 | none unless overridden | retries exhausted AND (no fallback registered OR fallback raised) |
| `design`, `release_readiness` (approval-gated) | 2 (applies to the stage handler itself) | none — an approval **rejection** skips retry entirely and rolls back immediately, since re-running the same content against a human "no" isn't a transient-failure case | exit gate fails, or `ApprovalRejected` |

Per-stage overrides (e.g. a real fallback for `implementation`) get registered when the
real Step 3 stage handlers are wired in — the mechanism is generic (`RetryPolicy` per
stage name), only the concrete fallback bodies are still domain-specific.

## 8. Scenario Notes (fill in during Day 3)

### Greenfield — custom aliases

**Requirement (raw):** "Add support for custom aliases so users can choose their own
short link instead of a generated one."

**Decomposition:** normalize requirement (new scenario-matched branch in
`orchestrator/stages/requirements.py`) → extend design doc with the new capability
(`orchestrator/stages/design.py`) → extend the actual implementation templates
(`orchestrator/stages/templates/service_app/{models,shortener,main}.py`) → extend the
test plan + real pytest suite (`orchestrator/stages/templates/service_tests/test_api.py`)
→ finalize docs. Same 8-stage graph as the baseline run — no graph changes were needed,
since "add an optional field + new validation/conflict path to an existing endpoint"
fits the existing implementation/test_planning/docs_drafting fan-out cleanly.

**Key design decisions (recorded as agent decisions in the run's `state.json`,
not just here):**
- Custom-alias collisions return `409 Conflict` instead of silently regenerating a
  substitute alias (the generated-alias behavior) — the caller asked for something
  specific and must get that or a clear "no."
- Idempotency for custom-alias requests is scoped to the exact `(alias, long_url)`
  pair, not `long_url` alone, so a custom-alias request can't be silently swallowed
  by the existing long_url-based idempotency check and return an unrelated old alias.
- Small reserved-word list (`{"api"}`) to avoid confusion with the existing route
  prefix, expected to grow as new top-level routes are added.
- No new endpoint — `custom_alias` is an optional field on the existing
  `POST /api/links`, since it's the same operation with an optional extra input,
  not a distinct capability.

**Orchestration:** ran via `python cli.py run --requirement "..."`
(`runs/run-20260817T070753-cfc760/`) — both approval checkpoints hit and approved,
`requirements` correctly matched the "custom alias" branch (see `state.json`'s
`requirement.normalized`/`assumptions`), `implementation` compiled clean,
`test_execution` ran 14 real pytest cases (7 baseline + 7 new) and passed, run
completed with `overall_status: complete`.

**Validation:** live smoke test via `uvicorn` + `curl` — custom alias creation,
409 on conflict with a different URL, 422 on the reserved word `api`, and 302
redirect through the custom alias, all confirmed against a running server (not
just `TestClient`).

### Brownfield (1/2) — link expiration / TTL

**Requirement (raw):** "Add link expiration (TTL) so short links can automatically expire."

**Codebase reasoning (shown to the user before writing code):** identified as touching
`service/app/db.py` (schema — new `expires_at` column, requiring an explicit
`ALTER TABLE` migration path since existing DB files predate the column and
`CREATE TABLE IF NOT EXISTS` alone won't add it), `models.py` (new optional
`ttl_seconds`/`expires_at` fields), `shortener.py` (`create_link` gains an
`expires_at` computation + idempotency-doesn't-extend rule; `get_long_url` needs
to distinguish "expired" from "never existed"), and `main.py` (redirect handler
needs a new response code). This is the actual brownfield characteristic: an
**existing data flow being extended**, not a fresh table — the migration path is
the part a greenfield feature wouldn't need.

**Key design decisions:**
- Redirect returns **410 Gone** for an expired alias, **404** for a never-existed
  one — distinct outcomes, since a caller might reasonably retry a 404 (typo) but
  should not retry a 410 (gone for good). The pre-existing 404 error message
  ("unknown or expired alias") had been anticipating exactly this split.
- Expiration enforced **lazily at read-time**, no background sweep — no scheduler
  needed for a single-process prototype; expired rows stay in the DB, just made
  unreachable via redirect.
- **Analytics stay readable after expiry** — expiry blocks the redirect (the
  thing that "uses" the link), not the stats endpoint (a read of history).
- **Idempotent repeats never extend expiry** — idempotent means no-op, not
  "refresh the TTL," consistent with how idempotency already worked for custom
  aliases.

**Orchestration:** ran via `python cli.py run --requirement "..."`
(`runs/run-20260817T102853-1395b5/`) — `requirements` matched the new TTL-scenario
branch, both approvals hit and approved, `test_execution` ran 21 real pytest cases
(14 prior + 7 new) and passed, `overall_status: complete`.

**Validation:**
- Schema migration tested directly: built a pre-TTL DB file by hand (no
  `expires_at` column, one legacy row), ran `init_db()` against it, confirmed the
  column was added via `ALTER TABLE` and the legacy row survived with
  `expires_at = None` (never expires — the correct default for pre-existing data).
- Live `uvicorn` smoke test with a **real 1-second TTL and real elapsed wall-clock
  time** (not just a backdated DB row): 302 while valid → 410 once the TTL
  genuinely elapsed → stats still 200 afterward.

### Brownfield (2/2) — rate limiting

**Requirement (raw):** "Add rate limiting to protect the service from abuse."

**Codebase reasoning (shown to the user before writing code):** new module
`service/app/rate_limit.py` (self-contained, not entangled with `db.py`/`shortener.py`
since this is a cross-cutting HTTP concern, not a domain rule about links), wired into
`main.py` as a FastAPI dependency on `POST /api/links` only. `requirements.py`/
`design.py`/`test_planning.py`/`docs_drafting.py` extended with the new scenario
branch, same pattern as TTL/custom-aliases.

**Key design decisions:**
- **Scoped to link creation only** — `POST /api/links` is the resource-consuming,
  abuse-prone operation; `GET /{alias}` redirects are deliberately NOT rate-limited,
  since a public redirect service needs reads to stay fast and always-available.
  Verified live: 5 rapid GETs after the creation limit was already exhausted all
  still returned normally (404 for the nonexistent test aliases used), never 429.
- **Fixed-window counter keyed by client IP**, in-memory, thread-safe (lock-guarded,
  same idiom as `orchestrator/runner.py`'s state mutation), configurable via
  `RATE_LIMIT_MAX_REQUESTS`/`RATE_LIMIT_WINDOW_SECONDS` — same env-var override
  pattern as `SHORTENER_DB_PATH`.
- **429 with `Retry-After`** on exceeded, so a well-behaved client can back off
  correctly rather than guess.
- **In-memory is a real limitation, not an oversight**: doesn't survive a restart,
  not shared across multiple app instances behind a load balancer. Documented in
  Section 9 rather than hidden.

**Orchestration:** ran via `python cli.py run --requirement "..."`
(`runs/run-20260817T163019-0e16a2/`) — `requirements` matched the new rate-limiting
branch, both approvals hit and approved, `test_execution` ran 24 real pytest cases
(21 prior + 3 new) and passed, `overall_status: complete`.

**Validation:**
- Test isolation problem caught and fixed during implementation: the rate limiter's
  state is process-global (a module-level dict), so without an explicit
  `rate_limit.reset()` in the test `client` fixture, earlier tests' POSTs would have
  silently counted against later tests' limits — a real cross-test contamination bug,
  not hypothetical, since the full suite makes 20+ creation calls across the file.
- Live `uvicorn` smoke test with `RATE_LIMIT_MAX_REQUESTS=3`: 3 creates succeed, 4th
  returns 429 with `Retry-After: 60`; 5 rapid redirect requests in the same window
  are never rate-limited.
